Step 1：采集当前 JD

目标：得到统一 raw_jd.jsonl

主工具MCP Jobs
为什么聚合 Boss、猎聘、智联、51job，字段更统一
辅助工具无。这个 Step 不引入其他爬虫
采集

具体使用方式

启动 MCP Jobs，固定查询词和城市，把原始结果原样保存。这个阶段不清洗、不抽技能，只负责可信落盘。

npx -y mcp-jobs # 调试模式 CRAWLER_HEADLESS=false CRAWLER_DEBUG=true npx -y mcp-jobs
查询词： AI Agent工程师、智能体开发工程师、Agent应用开发、大模型应用工程师、RAG工程师、MCP开发工程师 Java开发工程师、Java后端工程师、高级Java工程师、Java架构师
输出
data/raw/raw_jd_2026_mcp_jobs.jsonl
data/raw/queries.yaml
验收
raw JD >= 3000；平台 >= 3；Agent >= 500；Java >= 800
注意：MCP Jobs 主要拿当前数据，不负责历史 2024 数据。历史窗口要么补公开历史样本，要么在方案里明确“当前市场快照 + 持续月度更新”。

Step 2：清洗去重

目标：得到 clean_jd.parquet

主工具datasketch MinHash/LSH
辅助工具pandas/polars 做字段处理，rapidfuzz 做轻量字符串匹配
不做这个 Step 不抽技能、不判断新岗位
清洗

具体操作

先标准化字段，再用 hash 做精确去重，最后用 MinHash 找 JD 模板复制和近重复。

from datasketch import MinHash, MinHashLSH lsh = MinHashLSH(threshold=0.8, num_perm=128) # title_clean + company + description_clean -> shingles -> MinHash
quality_score = 0.25 * 字段完整度 + 0.25 * 描述长度合理性 + 0.20 * 发布时间可信度 + 0.15 * 来源可信度 + 0.15 * 非模板/非重复程度
输出
data/clean/clean_jd.parquet
data/report/cleaning_report.json
验收
clean JD >= 2000；重复率 < 5%；每条有 quality_score

Step 3：岗位归一

目标：每条 JD 都有 occupation_id

主工具sentence-transformers
辅助工具rapidfuzz 做明显同义合并；人工 alias 表做最终确认
归一

具体操作

用岗位标题加描述关键词做 embedding 聚类，把同义岗位合并成标准岗位簇。

from sentence_transformers import SentenceTransformer model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2") embeddings = model.encode(title_for_cluster_list) cosine_similarity >= 0.82 -> 候选同簇
输出
occupation_clusters.json
jd_with_occupation.parquet
occupation_alias.csv
验收
Agent 标题召回 >= 90%；Java 误合并 <= 10%

Step 4：技能抽取

目标：每个技能都有证据句

主工具LLM JSON 结构化抽取
辅助工具Chinese-SkillSpan 做标注规范；SkillSpan 做评测思想；技能词典兜底召回
边界LLM 只生成候选，不直接写入图谱
抽取

具体操作

LLM 输出固定 JSON，每个技能必须来自原文，并给出 evidence_sentence。然后用 100 条人工 gold 评测。

{ "raw_text": "K8s", "normalized_guess": "Kubernetes", "type": "technical_skill", "evidence_sentence": "熟悉 Docker/K8s，有微服务部署经验", "confidence": 0.86 }
Prompt 约束： 只从 JD 原文抽取，不允许补充常识。 每个技能必须给出 evidence_sentence。 不要抽“责任心、沟通能力、抗压能力”到技术技能主图。 输出必须是 JSON。
输出
skill_mentions.parquet
gold_jd_100.jsonl
skill_extraction_eval.json
验收
技术硬技能 span F1 >= 0.90；JSON 合法率 >= 98%

Step 5：技能标准化

目标：把 K8s / 容器编排归一成 Kubernetes

主工具ESCO 离线 CSV
辅助工具O*NET 只做 Java 基线解释；Lightcast 只做 top 技能抽样校验；中文 alias 表解决缩写和新词
标准化

具体操作

先查人工别名表，再查 ESCO preferred/alternative labels，再用 embedding 做候选匹配。未命中但高频的新技术进入 SkillCandidate。

raw_skill,normalized_skill,source,confidence K8s,Kubernetes,manual,0.98 容器编排,Kubernetes,manual,0.90 大模型,Large Language Models,manual,0.85 MCP,Model Context Protocol,manual,0.80
输出
skills_normalized.parquet
skill_alias.csv
skill_candidates.csv
验收
top 100 高频技能标准化率 >= 90%；新兴技能不丢弃

Step 6：新岗位发现

目标：证明 Agent 工程师是新兴岗位

主方法Job-SDF 的时序数据结构
辅助输入Step 3 岗位簇；Step 4/5 标准技能
不做不完整复现复杂预测模型，只复刻需求序列和共现图结构
发现

具体操作

按岗位和月份构造需求表、技能占比表、技能共现图，然后计算新岗位成熟度。

demand[occupation_id, month] = 去重 JD 数 skill_demand[occupation_id, skill_id, month] = 要求该技能的 JD 数 skill_proportion = skill_demand / 该岗位当月 JD 总数
maturity_score = 0.30 * log(growth_ratio) + 0.20 * demand_recent + 0.20 * source_diversity + 0.15 * skill_coherence + 0.15 * taxonomy_gap
输出
emerging_jobs_agent.json
agent_skill_profile.json
emerging_job_report.md
验收
至少 1 个新岗位案例；每个结论有 support_count / evidence_ids

Step 7：既有岗位能力更新

目标：输出 Java 新增、弱化、修改能力项

主方法窗口技能占比 diff
辅助工具O*NET 仅做既有岗位基线解释；Job-SDF 仅沿用表结构
为什么这个目标本质是统计 diff，不需要再引入复杂模型
更新

具体操作

对 Java 岗位簇比较 old_window 和 new_window 的技能占比，按规则分成新增、增强、弱化、修改。

p_old(skill) = old_window 中要求该技能的 Java JD 数 / old_window Java JD 总数 p_new(skill) = new_window 中要求该技能的 Java JD 数 / new_window Java JD 总数 delta = p_new - p_old growth = (p_new + 0.01) / (p_old + 0.01)
新增：p_old < 0.05 AND p_new >= 0.12 AND growth >= 2 增强：p_old >= 0.05 AND p_new >= 0.12 AND delta >= 0.10 弱化：p_old >= 0.12 AND delta <= -0.10 修改：技能仍存在，但上下文共现技能明显变化
输出
job_evolution_java.json
java_update_report.md
验收
至少 5 个能力变化项；每项有 p_old / p_new / evidence_ids

Step 8：Neo4j 建图

目标：可查询、可追溯的岗位能力图谱

主工具Neo4j Python Driver
辅助工具无。先不引入复杂 KG 框架
建图

具体操作

导入 JobPost、Occupation、Skill、Evidence、Snapshot 节点，再按月聚合生成 REQUIRES_SKILL 关系。

JobPost -[:POSTED_AS]-> Occupation JobPost -[:MENTIONS_SKILL]-> Skill Occupation -[:REQUIRES_SKILL {month, support_count, support_ratio, confidence}]-> Skill Skill -[:RELATED_TO {cooccur_count}]-> Skill Evidence -[:SUPPORTS]-> REQUIRES_SKILL
输出
scripts/import_neo4j.py
neo4j_dump/
docs/cypher_queries.md
验收
节点 >= 2000；关系 >= 5000；能查岗位、技能、证据、时间变化

Step 9：API 与解释层

目标：前端能展示结论和证据

主参考JobMatchAI 架构思想
辅助工具FastAPI 做接口；Elasticsearch 可选做全文检索
不照搬不复制 JobMatchAI 业务，只借确定性计算 + LLM 解释分离
服务

具体操作

算法层先算出 growth_ratio、support_count、confidence、evidence_ids；LLM 只能基于这些结果解释，不能改变分数或补充结论。

GET /api/emerging_jobs GET /api/job_evolution?occupation=Java开发工程师 GET /api/graph_data?occupation=AI Agent工程师&month=2026-06 GET /api/evidence?evidence_id=xxx
LLM 解释 prompt： 你只能根据以下 JSON 和 evidence 解释，不允许补充外部常识。 如果 evidence 不足，输出“证据不足”。
输出
backend/api.py
backend/schemas.py
data/api_mock/*.json
验收
4 个 API 返回 JSON；每个前端结论可点开 evidence
