# 30 份简历 BM25 与 BGE-M3 实验报告

## 1. 实验结论

本次已经跑通完整链路：

```text
30 份中文简历
-> Elasticsearch 字段加权 BM25 各召回 Top200
-> BAAI/bge-m3 编码简历与候选 JD
-> 在每份简历的 Top200 内计算余弦相似度并重排
-> 生成 6000 个可解释银标
```

BM25 适合快速缩小候选范围，BGE-M3 能明显改变排序并改善部分岗位族匹配，但当前纯语义排名仍会产生跨岗位族误排，暂时不能直接作为最终岗位推荐。

## 2. 数据与运行环境

- 简历：30 份脱敏中文简历。
- 岗位族：云计算、全栈、前端、后端、数据分析、数据工程、测试、移动开发、算法、运维，每类 3 份。
- 候选范围：3000 条企业岗位，不混入公务员岗位。
- Elasticsearch 索引：`chinese_jobs_v1`。
- Embedding 模型：`BAAI/bge-m3`。
- GPU：NVIDIA GeForce RTX 4060 Laptop GPU 8GB。
- 推理精度：FP16。
- 向量维度：1024。
- 最大文本长度：1024 tokens。
- 稳定 batch size：2。

本轮只检索企业岗位，是因为 30 份试验简历全部属于技术岗位。公务员岗位依赖专业、学历、政治面貌和基层经历等硬条件，后续应建立单独检索与评测流程。

## 4. BM25 召回结果

当前 BM25 使用字段加权：

```text
岗位标题 6.0
标签 5.0
采集关键词 4.0
JD 描述 2.5
公司名称 1.5
地点 1.2
汇总文本 1.0
```

运行统计：

| 指标 | 结果 |
|---|---:|
| 简历数 | 30 |
| 每份候选 | 200 |
| 候选总对数 | 6000 |
| 唯一候选岗位 | 587 |
| 整批查询耗时 | 约 1.93 秒 |
| Elasticsearch P50 | 49ms |
| Elasticsearch P95 | 95.2ms |
| Elasticsearch 最大延迟 | 144ms |

587 个唯一岗位在 6000 个候选位置中反复出现，说明当前候选池集中度较高。原因之一是企业数据主要来自腾讯和华为，岗位来源和职业类型覆盖仍不均衡。

## 5. BGE-M3 语义重排

BGE-M3 对 30 份简历和 587 个唯一岗位共 617 段文本编码，不重复计算相同 JD 向量。

| 指标 | 结果 |
|---|---:|
| 编码文本 | 617 |
| 编码耗时 | 21.65 秒 |
| 余弦相似度最小值 | 0.4076 |
| 余弦相似度均值 | 0.5514 |
| 余弦相似度 P50 | 0.5536 |
| 余弦相似度 P95 | 0.6172 |
| 余弦相似度最大值 | 0.7212 |
| 平均绝对名次变化 | 60.34 |
| 名次变化 P95 | 149.05 |
| BM25/BGE-M3 Top10 平均重合率 | 2.67% |

Top10 重合率很低，说明 BM25 和 BGE-M3 捕捉的是两种差异很大的信号。BM25 更依赖词项出现，BGE-M3 更依赖整体语义，但整体语义并不天然保证岗位族一致。

## 7. 银标如何生成

银标分数不是单独复制 BM25 或 BGE-M3 分数，而是组合四项透明信号：

```text
silver_score =
0.45 * BGE-M3 语义排名百分位
+ 0.20 * BM25 排名百分位
+ 0.20 * 简历技能在 JD 中的覆盖率
+ 0.15 * 意向岗位族匹配度
```

自动等级规则：

| 银标 | 规则 | 当前数量 | 占比 |
|---|---|---:|---:|
| 3 | 分数 >= 0.75 且岗位族强匹配 | 18 | 0.30% |
| 2 | 分数 >= 0.55，且岗位族或技能至少一项有效 | 378 | 6.30% |
| 1 | 分数 >= 0.35 | 2445 | 40.75% |
| 0 | 其余候选 | 3159 | 52.65% |

每条银标同时保存：BM25 名次、BM25 分数、语义名次、余弦相似度、岗位族匹配词、技能覆盖率和命中技能。因此后续能够追踪标签为什么生成。

银标只能用于：

- 构造人工标注候选池。
- 训练或微调阶段的弱监督样本。
- 筛选困难正样本和困难负样本。
- 检查系统不同模块的分歧。

银标不能替代人工金标，也不能用来宣称模型的真实准确率。

## 8. 当前机器排序方式

当前存在三种顺序：

1. **BM25 顺序**：按照 Elasticsearch 字段加权词项相关性排序，用于快速召回 Top200。
2. **BGE-M3 顺序**：在固定 Top200 内，按照简历向量和完整 JD 向量的余弦相似度从高到低排序。
3. **银标分数**：组合语义名次、BM25 名次、技能覆盖和岗位族匹配，当前用于生成弱标签，不是线上最终排序。

`bge_m3_reranked_top200_30.jsonl` 展示的是第 2 种纯语义顺序；`resume_job_rankings_30.csv` 同时保留三类信息，便于对照。

## 9. 当前排序需要怎样优化

### 9.1 岗位族先约束，再做语义排序

当前最大问题是语义相近但岗位不同，例如：

- 数据分析 -> 财经专员。
- 运维 -> 物流经理。
- 前端/移动开发 -> 服务器开发。
- 后端 -> 前端开发。

下一版应将岗位族作为门控条件或高权重特征，而不是只占银标的 15%。可以先把同岗位族放在主候选区，再允许少量相邻岗位作为探索候选。

### 9.2 拆分简历与 JD 字段

当前将整份简历和整段 JD 各压成一个向量。下一版可以分别编码：

- 意向岗位与岗位标题。
- 简历技能与 JD 技能要求。
- 工作/项目经验与岗位职责。
- 学历专业与硬条件。

再根据岗位类型组合分数，减少长文本中的通用描述干扰。

### 9.3 加入 Cross-Encoder 精排

BGE-M3 适合快速双塔相似度，但不直接联合阅读简历和 JD。建议仅对 Top50 使用中文 Cross-Encoder 或经过人岗数据微调的重排模型，判断具体条件是否真正对应。

### 9.4 使用金标学习权重

当前权重是透明的工程初始值。完成约 600 对人工试标后，可以使用 Logistic Regression、LightGBM 或 Learning-to-Rank 学习 BM25、Embedding、岗位族、技能覆盖、经验和硬条件的合理权重。

## 10. Neo4j 能否继续优化

可以，但 Neo4j 的价值不应是直接替代 BM25 或 BGE-M3，而是增加结构化知识信号。

建议图结构：

```text
(Resume)-[:HAS_SKILL]->(Skill)
(Job)-[:REQUIRES_SKILL]->(Skill)
(Job)-[:BELONGS_TO]->(JobFamily)
(Skill)-[:ALIAS_OF]->(Skill)
(Skill)-[:RELATED_TO]->(Skill)
(JobFamily)-[:ADJACENT_TO]->(JobFamily)
```

它可以帮助：

- 将 `K8s`、`Kubernetes` 等别名统一，提升技能召回。
- 通过关联技能发现可迁移能力，例如 Python -> 数据处理 -> 数据工程。
- 对跨岗位族结果施加图距离惩罚，减少运维 -> 物流经理等漂移。
- 补充 BM25/BGE-M3 未进入 Top200 但图谱证据充分的岗位。
- 输出已匹配技能、缺失技能和可学习路径，增强可解释性。

风险是图扩展过宽会引入更多噪声。因此必须比较：

```text
BM25
BM25 + BGE-M3
BM25 + BGE-M3 + Neo4j
BM25 + BGE-M3 + Neo4j + 学习排序
```

只有在人工金标上的 `Recall@200`、`NDCG@10` 或 `MRR` 提升，才能证明图谱确实优化了排序。

## 11. 下一步实验

1. 每份简历从 BM25 高排、BGE-M3 高排、两者分歧和随机负样本中抽取约 20 条，共约 600 对。
2. 按 0-3 级完成双人独立金标，并记录硬条件、匹配技能和缺失技能。
3. 使用金标计算 BM25 `Recall@200` 和 BGE-M3 `NDCG@5/10`、`MRR`。
4. 实现岗位族门控和技能字段分项相似度，重跑同一固定候选池。
5. 建立 Neo4j 第一版技能图谱，并完成加入图谱前后的消融对比。

当前实验的真正成果不是“模型已经准确”，而是完整、可复现地跑通了两阶段检索，并清楚定位了下一轮需要解决的岗位族漂移和硬条件缺失问题。
