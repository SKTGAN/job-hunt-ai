# 项目目标与阶段计划

本文档用于明确当前项目下一阶段要做什么。目标围绕比赛题目《多源异构数据驱动岗位和能力图谱构建与动态演化分析研究》展开。

当前核心方向不是继续沿用原项目里的国外英文岗位数据，而是把系统改造成面向中文本地招聘市场的“岗位能力图谱动态演化与人岗匹配系统”。

## 1. 总体目标

最终要完成一套可以演示和评测的系统：

```text
中文多源岗位 JD 采集
-> 中文 JD 清洗与解析
-> 岗位能力图谱构建
-> 新岗位发现与定义
-> 既有岗位能力动态更新
-> 中文简历解析
-> 人岗匹配度诊断
-> 能力差距分析
-> 学习路径与改进建议
```

比赛看重的不是单点功能，而是从数据采集到图谱构建，再到简历匹配和分析建议的完整闭环。

## 2. 当前第一阶段目标

第一阶段先做三件事：

1. 把中文岗位 JD 数据“扒下来”。
2. 准备中文简历数据和后续人工标注数据。
3. 把 Neo4j 图数据库完全本地化，并让中文岗位能力图谱能写进去。

这一阶段不急着做漂亮界面，先把数据和图谱底座打稳。

## 3. 目标一：中文岗位 JD 数据采集

### 3.1 目标说明

把原项目中的英文岗位数据换成本地中文招聘数据。

优先采集以下方向的岗位 JD：

| 方向 | 示例岗位 |
| --- | --- |
| 人工智能 | AI工程师、大模型应用开发、AI Agent工程师、RAG工程师、NLP算法工程师、多模态算法工程师 |
| 大数据 | 大数据开发工程师、数据仓库工程师、数据治理工程师、Flink工程师 |
| 智能系统 | 智能制造工程师、机器人算法工程师、智能驾驶算法工程师、嵌入式AI工程师 |
| 物联网 | 物联网工程师、IoT平台开发、嵌入式开发、工业互联网工程师 |
| 既有岗位样例 | Java开发工程师、Python开发工程师、前端开发工程师、数据分析师 |

### 3.2 第一批采集目标

先不要追求特别大规模，第一批目标是：

| 数据类型 | 数量目标 |
| --- | --- |
| 原始中文 JD | 1000 条左右 |
| 用于人工标注的 JD | 100 条 |
| 新岗位样例 | 1 个，例如 AI Agent 工程师 |
| 既有岗位样例 | 1 个，例如 Java 开发工程师 |

### 3.3 推荐采集来源

优先使用中文招聘平台和企业官网：

| 数据源 | 作用 |
| --- | --- |
| Boss直聘 | 获取最新市场岗位需求 |
| 猎聘 | 获取中高端岗位和企业职位描述 |
| 智联招聘 | 获取传统岗位和城市覆盖 |
| 51job | 获取较广泛的岗位样本 |
| 拉勾 | 获取互联网技术岗位 |
| 企业官网招聘页 | 作为高可信度数据源 |
| 政府职业标准/人社部新职业 | 作为标准岗位定义参考 |

可以尝试使用 `mergedao/mcp-jobs` 作为中文岗位采集工具，先把职位列表和职位详情导出为 JSON。

## 4. 目标二：中文简历数据与标注数据准备

### 4.1 目标说明

比赛要求简历提取准确率 >= 90%，所以不能只靠随便上传一份简历演示。必须准备可评测的中文简历样本和人工标注结果。

### 4.2 简历数据目标

| 数据类型 | 数量目标 |
| --- | --- |
| 中文 PDF 简历 | 30-50 份 |

| 人岗匹配测试样本 | 至少 100 组“简历-岗位”匹配样本 |

### 4.3 简历需要标注的内容

## 5. 目标三：Neo4j 本地化

### 5.1 目标说明

Neo4j 要完全本地部署，用来存储中文岗位能力图谱。

当前项目已经在 `docker-compose.yml` 中使用了本地 Neo4j 容器：

```text
Neo4j Browser: http://localhost:7474
Bolt URI: bolt://localhost:7687
Username: neo4j
Password: password
```

下一步不是替换 Neo4j，而是让它存入中文岗位、技能、证据和演化关系。

### 5.2 Neo4j 需要存储的节点

```text
(:Job) 岗位
(:JobFamily) 岗位族，例如 Java开发工程师、AI Agent工程师
(:Skill) 技能点
(:SkillCategory) 技能类别，例如 编程语言、框架、算法、工具
(:Company) 公司
(:Industry) 行业
(:Location) 城市/地区
(:Evidence) 原始JD证据
(:TimeWindow) 时间窗口
(:Candidate) 简历候选人
(:Resume) 简历
```

### 5.3 Neo4j 需要存储的关系

```text
(:Job)-[:BELONGS_TO]->(:JobFamily)
(:Job)-[:REQUIRES_SKILL]->(:Skill)
(:Job)-[:PREFERS_SKILL]->(:Skill)
(:Job)-[:OFFERED_BY]->(:Company)
(:Job)-[:LOCATED_IN]->(:Location)
(:Job)-[:BELONGS_TO_INDUSTRY]->(:Industry)
(:Skill)-[:BELONGS_TO_CATEGORY]->(:SkillCategory)
(:Skill)-[:SUPPORTED_BY]->(:Evidence)
(:Job)-[:APPEARS_IN]->(:TimeWindow)
(:Candidate)-[:HAS_SKILL]->(:Skill)
(:Candidate)-[:MATCHES]->(:Job)
```

### 5.4 本地化要求

Neo4j 本地化需要做到：

- Docker 本地启动，不依赖云服务。
- 数据通过 volume 持久化。
- 可以备份和恢复。
- 后端可以稳定连接。
- 中文节点和中文关系属性能正常写入和查询。
- 能通过 Neo4j Browser 看到中文岗位能力图谱。

### 5.5 本阶段产出

```text
scripts/
  neo4j/
    init_constraints.cypher
    import_chinese_jobs.cypher
    demo_queries.cypher
```

第一阶段完成标准：

- `docker compose up -d neo4j` 能启动本地 Neo4j。
- 能写入至少 100 条中文岗位。
- 能写入岗位-技能关系。
- 能查询某个岗位的技能图谱。
- 能查询某个技能关联的岗位。
- 能备份 Neo4j 数据。

### 7.1 目标说明

比赛明确要求发现“市场上正在萌芽但尚未标准化或逐渐兴起的新岗位”。

建议第一版选择：


```text

可信度
```

### 7.3 方法

```text
-> 标题归一化

-> 技能组合统计
-> 多源交叉验证

-> 证据校验
-> 人工确认
```

完成标准：

- 能输出 1 个新岗位定义。

### 8.1 目标说明

比赛要求针对现有岗位识别能力要求变化，明确新增、删除、修改能力项。

建议第一版选择：

```text

```

### 8.2 需要输出

```json
{
  "job_family": "Java开发工程师",
  "added_skills": ["Kubernetes", "云原生", "大模型API集成"],
  "removed_skills": ["Struts"],
  "rising_skills": ["Spring Cloud", "微服务", "分布式事务"],
  "declining_skills": ["JSP"],
  "modified_skills": [
    {
      "from": "SSM",
      "to": "Spring Boot + Spring Cloud",
      "reason": "岗位职责从传统Web系统开发转向微服务架构"
    }
  ]
}
```

### 8.3 方法

```text

-> 抽取每个窗口的技能频次
-> 计算技能变化
-> 多源验证
-> 输出新增/删除/增强/减弱/修改
-> 写入 Neo4j
-> 前端展示演化结果
```

完成标准：

- 至少完成 1 个既有岗位能力演化样例。
- 能展示技能变化证据。
- 能解释为什么某个技能新增或热度上升。
- 能支持人工优化。
